## Что изменено

- Компактный игровой стол, вкладки сценария/бункера/хроники и панели ведущего, отдельная мобильная навигация. Обновление комнаты сохраняет активную вкладку и незавершённый ввод. Модальные окна поддерживают Escape, клавиатуру и восстановление фокуса.
- Запуск партии, раздача, переходы фаз и таймер выполняются на сервере. Старт проверяет готовность; повторная раздача не создаёт дубликаты. Таймер можно запустить, остановить, продолжить, сбросить, увеличить/уменьшить или задать вручную. Нулевая длительность отключает автоматический отсчёт.
- Ведущий настраивает количество карт по категориям, повторы обычных карт и спецусловий, раскрытия по раундам. Можно добавлять карты, редактировать существующие, менять ресурсы и свойства бункера. Мут, таймаут, снятие ограничений, исключение и возвращение игрока проверяют права ведущего.
- Спецусловия выполняются одной транзакцией: проверка владельца, целей, защиты и доступности, изменение карт, расходование и запись результата. Слепой выбор не получает скрытый текст; обмен переносит содержание вместе с признаком раскрытия. Бункерные эффекты используют тот же журнал. Клонирование выбирает реально выполненный эффект в текущем раунде.
- Голоса проверяются на сервере, повторная отправка запрещена; учитываются вес, блокировки, защита и специальные правила ничьей. Подробные голоса и снимки карточек доступны ведущему, приватные подсказки — получателю.
- В мастер-панели есть фильтруемый журнал последних 300 событий, приватные подробности обменов, модерации и ручных изменений. Ведущий рассматривает запрос на обязательную категорию следующего раскрытия и может снимать активные условия с записью в журнал.

## Установка

1. Завершите текущие партии и сохраните резервную копию базы. Этот выпуск меняет модель идентификации: прежние комнаты с произвольными ID игроков нужно создать заново.
2. В Supabase Auth включите Anonymous Sign-Ins. В Bot and Abuse Protection включите CAPTCHA, выберите Cloudflare Turnstile и сохраните Secret Key от того же виджета, чей публичный Site Key указан в `js/auth.js`. В Turnstile разрешите домен `alive-project-eta.vercel.app` и выберите режим Managed. Секретный ключ хранится только в Supabase. Клиент получает анонимную авторизованную сессию после проверки; регистрации и пароля для игрока нет. Нужен обычный публичный ключ проекта, не service-role ключ.
3. Сначала проверьте выпуск на тестовом проекте с текущей схемой и справочниками. Выполните `supabase/release.sql` целиком. Файл рассчитан на существующую схему AliveProject, включая изменения 0020–0022; он не создаёт пустую базу с нуля. В нём одна транзакция, политики доступа, серверные функции и уведомление для обновления API.
4. Во время согласованного обновления примените SQL к рабочей базе и опубликуйте клиент из этой ветки. Старый клиент несовместим с новыми ограничениями доступа. Не публикуйте только JavaScript без SQL или наоборот при активных партиях.
5. Создайте новую комнату и проверьте игру из двух независимых браузерных профилей: готовность, старт, скрытые карты, обмен, голосование и действия ведущего.

В рабочей базе ранее были разрешающие всем политики и привилегированные функции, доверявшие переданному ID игрока. Выпуск заменяет их проверками Auth/RLS и закрывает прежние обходные RPC. Объяснение проверки Supabase: [исполнение SECURITY DEFINER анонимной ролью](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable).

## Проверки и границы автоматизации

- `tests/database.sql`: права игрока/ведущего, скрытые сведения, атомарность обмена, расходование карты, приватная подсказка, таймер, чат, номинация и голосование.
- `tests/database-extended.sql`: ничья, открытое голосование и шпион, пустое голосование, переходы фаз, устаревшая версия состояния, защита карт, несколько карт одной категории и строгие повторы.
- `tests/effects.sql`: 81 вариант диспетчера спецусловий. Для каждого проверены успешное выполнение/запрос ведущему, расходование и журнал; дополнительно — восстановление значения и отсутствие двойной блокировки бункера. Это проверка ветвей выполнения, а не доказательство всех возможных сочетаний 81 условия.
- `tests/start-and-host.sql`: обратный отсчёт, запрет преждевременного старта, раздача готовых персонажей с целями, таймер раскрытия, задержка свойства, снятие условия и закрытие прежних привилегированных RPC.
- `tests/browser.cjs`: Chromium, ведущий/игрок/лобби, ширина 390 px, вкладки, сохранение ввода, модальные окна и лимиты повторных раскрытий. Браузерная проверка использует подменённый транспорт Supabase; реальная работа SQL проверяется отдельными интеграционными тестами.

Нарративные условия и решения о катастрофах/нарушениях остаются решениями ведущего. Их флаги отображаются и могут быть сняты после применения; автоматическая оценка произвольного события по тексту не выполняется. Неизвестный ключ механики возвращает ошибку и не тратит карту.

В случайном пуле проекта отсутствуют личные цели: по умолчанию они выдаются только готовым персонажам. Принудительное включение отсутствующей категории сообщает о недостатке карт. Настройки генерации влияют на будущую раздачу и замену карт, а не переписывают автоматически уже выданные характеристики.

## Повторный запуск тестов

Для браузера: Node.js, Google Chrome и Playwright 1.62.1; выполните `node tests/browser.cjs`. Если библиотеки доступны через общий runtime, задайте NODE_PATH к его node_modules. Скриншоты создаются в корне проекта.

Проверка CAPTCHA: `node tests/auth.cjs` проверяет передачу токена в Supabase, запрет отправки без токена, повторных запросов и повторного использования токена, истечение проверки и ошибку загрузки скрипта. Транспорт и Turnstile подменены тестовыми ответами. Настоящую проверку нужно пройти после публикации на разрешённом домене в новом браузерном профиле. Для обновления только CAPTCHA замените `index.html`, `js/gameplay.js` и добавьте `js/auth.js`; повторное выполнение SQL не требуется.

Для базы: `node tests/build-database-check.cjs` создаёт `tests/database-check.generated.sql`. Запустите полученный файл целиком в SQL Editor тестового проекта с исходной схемой. Он содержит выпуск, все проверки и ROLLBACK. Не запускайте отдельные файлы тестов против рабочей базы: для них необходим общий контекст транзакции. Проверки создают только комнату `__ALIVE_TEST__`; при занятом коде вставка завершится ошибкой.

ROLLBACK отменяет строки и схему, но Postgres не возвращает использованные значения последовательностей: после проверки возможны пропуски ID.
